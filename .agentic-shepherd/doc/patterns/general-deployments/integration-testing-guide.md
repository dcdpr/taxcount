# Integration Testing with Insta Snapshots

This guide covers setting up integration tests in Rust projects using
the single test binary pattern and gargoyle-snaps for snapshot testing.

Integration tests keep test code out of `src/` and, when consolidated into one binary, run faster (see section 1).

## 1. Why One Test Binary

### The Problem

As documented in [matklad's article](https://matklad.github.io/2021/02/27/delete-cargo-integration-tests.html), each file in `tests/` becomes a separate binary. Cargo must re-link
the library crate with each integration test, causing:

- **3x slower compilation** - linking overhead multiplies
- **5x larger disk artifacts** - each binary includes the full crate
- **Repeated fixture setup** - expensive operations run per-binary

### The Solution

Consolidate all integration tests into `tests/it/main.rs`:

```rust
// tests/it/main.rs
mod test_error;
mod test_utils;
mod utils;

mod feature_one_test;
mod feature_two_test;
mod cli_test;

pub static SNAPSHOTS_DIR: &str = concat!(env!("CARGO_MANIFEST_DIR"), "/snapshots");
pub static FIXTURES_DIR: &str = "fixtures";
```

### Benefits

- **One compilation** - link once, run all tests
- **Shared fixtures** - `OnceLock` singletons for expensive setup
- **Cross-file imports** - utilities accessible via `crate::`
- **Faster CI** - minutes become seconds

## 2. Directory Structure

```
project/
  tests/
    it/
      main.rs              # Module declarations, constants
      test_error.rs        # Unified error type
      test_utils.rs        # Helper functions FOR tests (fixtures, temp files)
      test_utils/
        test_fixtures.rs   # Submodules of test helpers
        file_fixtures.rs   # Temp file/dir creation
      utils.rs             # Tests OF src/utils module (not test helpers!)
      utils/
        allowlist_test.rs  # Tests OF src/utils/allowlist
      feature_test.rs      # Tests for feature
      cli_test.rs          # CLI command tests
  fixtures/                # Static test data files
  snapshots/               # Generated by insta (do not edit)
  Cargo.toml
```

**Naming collision warning**: `test_utils.rs` provides test infrastructure,
while `utils.rs` contains tests for your `src/utils` module. The names look
similar but serve completely different purposes.

### Naming Convention

Test files should end with `_test.rs`. gargoyle-snaps derives snapshot
prefixes from filenames by stripping `_test`:

- `cli_test.rs` → `cli__snapshot_name.snap`
- `feature_test.rs` → `feature__snapshot_name.snap`

### Access Visibility

Tests in `tests/it/` can only import what `lib.rs` makes public:

```rust
// tests/it/feature_test.rs
use your_crate::PublicType;           // ✓ lib.rs exposes this
use your_crate::internal::Private;    // ✗ not public in lib.rs
use crate::test_utils::helper;        // ✓ test-internal utilities
```

This differs from `src/main.rs` which has full access to all modules.
See "Rust Module Architecture" in CLAUDE.md for the full explanation
of separate module trees.

### Don't Use tests/*.rs Pattern

<example_failure>
<reason>each file becomes a separate binary, slower compilation, can't share test utilities</reason>
Avoid placing test files directly in `tests/`:
```
tests/
  issue_test.rs        # ❌ Each file becomes a separate binary
  parsing_test.rs      # ❌ Slower compilation
  catharsis_test.rs    # ❌ Can't easily share test utilities
```
</example_failure>

Always use `tests/it/` with a single `main.rs` entry point.

## 4. Snapshot Macros (gargoyle-snaps)

### Three Macro Variants

```rust
use gargoyle_snaps::{assert_snapshot_text, assert_snapshot_json, assert_snapshot_debug};

// For string output
assert_snapshot_text!(
    "snapshot_name",
    "Brief description of what this tests.",
    "Why this test exists - the invariant being verified.",
    "Concrete values to check: field=value, structure has N items",
    string_result,
);

// For serializable types (JSON format)
assert_snapshot_json!(
    "snapshot_name",
    "Brief description.",
    "Invariant being verified.",
    "Expected: status=success, items.len()=3",
    &serializable_value,
);

// For Debug-only types
assert_snapshot_debug!(
    "snapshot_name",
    "Brief description.",
    "Invariant being verified.",
    "Expected structure properties",
    &debug_value,
);
```

### The Independent Verification Principle

**The `expected_output` parameter must be human-written.**

When reviewing a snapshot, you need an independent reference point.
If `expected_output` is generated from the code being tested, and the
code has a bug, the guidance will also be wrong.

```rust
// WRONG - derived from code
let expected = format!("items={}", result.items.len());
assert_snapshot_json!("test", "desc", "purpose", &expected, &result);

// RIGHT - human-written based on requirements
assert_snapshot_json!(
    "parsed_config",
    "Parse config.toml with three sections.",
    "All sections must be preserved during parsing.",
    "sections.len()=3, has 'database', 'server', 'logging' keys",
    &parsed_config,
);
```

### Reviewer Flow

When reviewing snapshots, check in order:

1. **desc** → "What am I looking at?"
2. **test_purpose** → "Why does this matter?"
3. **expected_output** → "What specific values should I verify?"
4. Compare against actual snapshot content

## 5. Fixture Strategies

### Strategy 1: Inline Strings

For simple tests with minimal setup:

```rust
use crate::utils::file_fixtures::create_temp_dir_with_files;

#[test]
fn test_parse_config() {
    let files = [
        ("config.toml", "[server]\nport = 8080\n"),
        ("data.json", r#"{"key": "value"}"#),
    ];

    let temp_dir = create_temp_dir_with_files(&files)
        .expect("Failed to create temp dir");

    let config = parse_config(temp_dir.path().join("config.toml"))
        .expect("Failed to parse");

    assert_snapshot_json!(
        "simple_config",
        "Parse minimal server config.",
        "Port value must be extracted correctly.",
        "port=8080",
        &config,
    );
}
```

### Strategy 2: Single Temp File

When you only need one file:

```rust
use tempfile::NamedTempFile;
use std::io::Write;

fn create_temp_file(content: &str) -> NamedTempFile {
    let mut file = NamedTempFile::new().expect("Failed to create temp file");
    write!(file, "{}", content).expect("Failed to write");
    file
}

#[test]
fn test_validate_single_file() {
    let file = create_temp_file("invalid content here");

    let result = validate_file(file.path());

    assert!(result.is_err());
}
```

### Strategy 3: Static Fixtures

For complex test data, use files in `fixtures/`:

```rust
use crate::FIXTURES_DIR;
use std::path::Path;

#[test]
fn test_complex_document() {
    let content = fs_err::read_to_string(
        Path::new(FIXTURES_DIR).join("complex-document.md")
    ).expect("Failed to read fixture");

    let parsed = parse_document(&content).expect("Failed to parse");

    assert_snapshot_json!(
        "complex_doc",
        "Parse document with nested sections.",
        "All nesting levels must be preserved.",
        "sections=5, max_depth=3, has footnotes",
        &parsed,
    );
}
```

### Strategy 4: Combined

Load fixtures and combine with dynamic content:

```rust
#[test]
fn test_merge_documents() {
    let base = fs_err::read_to_string(
        Path::new(FIXTURES_DIR).join("base-template.md")
    ).expect("Failed to read base");

    let files = [
        ("template.md", base.as_str()),
        ("additions.md", "## New Section\n\nAdded content.\n"),
    ];

    let temp_dir = create_temp_dir_with_files(&files)?;

    let merged = merge_documents(temp_dir.path())?;

    assert_snapshot_text!(
        "merged_doc",
        "Merge template with additions.",
        "New section must appear after existing content.",
        "Contains '## New Section', original headers preserved",
        &merged,
    );
}
```

### Choosing a Strategy

| Scenario | Strategy |
|----------|----------|
| Simple content, few files | Inline strings |
| Single file validation | NamedTempFile |
| Complex realistic data | Static fixtures |
| Base + modifications | Combined |

## 6. TestError Pattern

Create a unified error type for test functions:

```rust
// tests/it/test_error.rs
use your_crate::{ParseError, ValidationError, IoError};

#[derive(Debug, onlyerror::Error)]
pub enum TestError {
    #[error("Parse error: {0}")]
    Parse(#[from] ParseError),

    #[error("Validation error: {0}")]
    Validation(#[from] ValidationError),

    #[error("IO error: {0}")]
    Io(#[from] std::io::Error),
}
```

### Usage

```rust
use crate::test_error::TestError;

#[test]
fn test_full_workflow() -> Result<(), TestError> {
    let input = fs_err::read_to_string("fixtures/input.txt")?;
    let parsed = parse(&input)?;
    let validated = validate(&parsed)?;

    assert_snapshot_json!(
        "workflow_result",
        "Complete parse-validate workflow.",
        "Validation must accept well-formed input.",
        "status=valid, warnings=0",
        &validated,
    );

    Ok(())
}
```

### Benefits

- No `.unwrap()` chains obscuring test logic
- `?` propagation works naturally
- Error context preserved for debugging
- Type-safe error handling

## 7. CLI Testing with Typed Outputs

### Define Output Types

```rust
// In your crate
use serde::{Deserialize, Serialize};

#[derive(Debug, Serialize, Deserialize)]
pub struct CommandSuccess {
    pub status: String,
    pub items_processed: usize,
    pub warnings: Vec<String>,
}

#[derive(Debug, Serialize, Deserialize)]
pub struct CommandError {
    pub error: String,
    pub code: i32,
}

#[derive(Debug, Serialize, Deserialize)]
#[serde(untagged)]
pub enum CommandOutput {
    Success(CommandSuccess),
    Error(CommandError),
}
```

### Command Runner Helper

```rust
// tests/it/test_utils.rs
use std::{path::Path, process::Command};

pub struct CommandResult {
    pub success: bool,
    pub stdout: String,
    pub stderr: String,
}

pub fn run_command(args: &[&str], dir: &Path) -> CommandResult {
    let bin_path = env!("CARGO_BIN_EXE_your-binary");

    let output = Command::new(bin_path)
        .args(args)
        .current_dir(dir)
        .output()
        .expect("Failed to execute command");

    CommandResult {
        success: output.status.success(),
        stdout: String::from_utf8_lossy(&output.stdout).to_string(),
        stderr: String::from_utf8_lossy(&output.stderr).to_string(),
    }
}
```

### Test with Typed Output

```rust
use crate::test_utils::run_command;
use your_crate::CommandOutput;

#[test]
fn test_process_command() {
    let temp_dir = create_temp_dir_with_files(&[
        ("input.txt", "data to process"),
    ]).expect("Failed to create temp dir");

    let result = run_command(
        &["process", "--input", "input.txt", "--json"],
        temp_dir.path(),
    );

    assert!(result.success, "Command failed: {}", result.stderr);

    let output: CommandOutput = serde_json::from_str(&result.stdout)
        .expect("Failed to parse JSON output");

    assert_snapshot_json!(
        "process_success",
        "Process command with valid input.",
        "Must report success with item count.",
        "status='ok', items_processed > 0, warnings empty",
        &output,
    );
}
```

### Testing Error Cases

```rust
#[test]
fn test_process_missing_file() {
    let temp_dir = tempfile::TempDir::new().expect("Failed to create temp dir");

    let result = run_command(
        &["process", "--input", "nonexistent.txt", "--json"],
        temp_dir.path(),
    );

    assert!(!result.success, "Command should have failed");

    let output: CommandOutput = serde_json::from_str(&result.stdout)
        .expect("Failed to parse JSON output");

    assert_snapshot_json!(
        "process_missing_file",
        "Process command with missing input file.",
        "Must return file-not-found error.",
        "error contains 'not found', code != 0",
        &output,
    );
}
```

## 8. Built-in Filters

gargoyle-snaps automatically applies filters to normalize:

### Timestamps

```
2024-01-15T10:30:00Z          → [timestamp]
2024-01-15T10:30:00+05:00     → [timestamp]
[claude 20250115 10:30 UTC]   → [USERNAME YYYYMMDD HH:MM UTC]
20250115 10:30 UTC            → YYYYMMDD HH:MM UTC
```

### Temporary Paths

```
/var/folders/xx/yy/T/tmp.abc123/  → [tmp]/
/tmp/claude/session123/           → [tmp]/
/private/tmp/claude/xyz/          → [tmp]/
```

### Debug DateTime Fields

```
datetime: "2025-01-15T..."  → datetime: "[DATETIME]"
```

### Adding Project-Specific Filters

gargoyle-snaps applies `usual_filters()` automatically. To add
project-specific filters:

1. **Extend gargoyle-snaps** - add patterns to `usual_filters()` in
   the crate, or add a parameter to the macros
2. **Use raw insta** - bypass gargoyle-snaps for tests needing custom
   filters (loses the macro conveniences)

The built-in filters cover most needs. Custom filters are rarely required.

### Filter Order (in gargoyle-snaps)

The built-in filters are ordered specific-to-general. This matters
because regex filters are applied in order - the first match wins:

```
// gargoyle-snaps orders these correctly:
1. [claude 20250115 10:30 UTC]  →  [USERNAME YYYYMMDD HH:MM UTC]  (specific)
2. 20250115 10:30 UTC           →  YYYYMMDD HH:MM UTC             (general)
```

If reversed, the general pattern would match first and the bracketed
username format would never be recognized.

## 9. Workflow

### Running Tests

Use the cargo aliases defined in `.cargo/config.toml`:

```bash
# Run all tests (workspace, all targets, no-fail-fast, --frozen)
cargo test-all

# Run all tests and allow crate updates (use when Cargo.lock is stale)
cargo test-all-update-crates

# Run specific test
cargo test --test it test_name

# Run with output
cargo test --test it -- --nocapture

# Run ignored tests
cargo test-ignored

# Insta snapshot management
cargo ir                            # insta review --workspace
cargo insta-snapshots-unused-find   # find unreferenced snapshots
cargo insta-snapshots-unused-delete # delete unreferenced snapshots
```

### Snapshot Review Process

1. **Run tests** - new snapshots create `.snap.new` files
2. **(Claude should) Read the full `.snap.new` file** - understand what changed
3. **Never edit `.snap.new` directly** - fix code if wrong
4. **(for human) Run `cargo ir`** - insta review to accept or reject

### When Snapshots Fail

If a snapshot doesn't match:

1. Read the `.snap.new` file completely
2. Compare with `.snap` to understand the diff
3. If the new output is wrong → fix the code, not the snapshot
4. If the new output is correct → report why to human and suggest `cargo insta review`

### Pre-commit Hook

The installed pre-commit hook:

- Runs `cargo test-all` before allowing commits
- Fails if any `.snap.new` files exist (unreviewed snapshots)
- Ensures committed code has passing tests

## Summary

1. **One binary** - consolidate tests in `tests/it/main.rs`
2. **gargoyle-snaps** - use typed macros with human-written expectations
3. **Fixtures** - choose strategy based on complexity
4. **TestError** - unified error type with `onlyerror::Error`
5. **Typed CLI output** - deserialize JSON, snapshot the typed result
6. **Filters** - automatic normalization, custom when needed
7. **Workflow** - read snapshots fully, never edit `.snap.new`
